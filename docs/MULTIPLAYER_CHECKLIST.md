## Automatic loot — production feature not yet field-tested

The earlier development log confirmed friend lookup and one Group Loot → FFA → Group Loot probe in a two-player outdoor party. It does not pass the production checks below, and contains no dungeon-policy test. Only the leader needs this addon for automatic loot; use normal party loot controls to inspect results.

- [ ] **Defaults and UI:** open `/zkir` in 1.3.1. Fresh settings must have both Auto FFA options off; upgrading must preserve existing choices. Check the always-on dungeon Group Loot explanation, checkbox labels, live status and the character editor at Small/Normal/Large scales. Save several `Name-Realm` entries, try a name without a realm, an invalid entry and Cancel/Escape; reload and verify persistence. Diagnostic commands and probe controls must be absent.
- [ ] **Friends outdoors:** as leader, enable only friends in a connected, out-of-combat two-player party with a Battle.net friend. Begin with Group Loot. After roughly two seconds, confirm actual FFA and status; confirm no automatic-loot party-chat traffic. Repeat outdoors with 3–5 people and an alternate character. Record failures without assuming friend identity from a display name. Dungeon expectations are Group Loot, as covered separately below.
- [ ] **Characters and mixtures:** disable friends, list the exact other characters and enable characters. Test a same-name different-realm member and a stranger: neither should qualify. Enable both options and mix friends with explicitly listed nonfriends; everyone must match an enabled option. Other members can have the addon disabled.
- [ ] **Trust loss:** after addon-set FFA, invite a stranger, disconnect a member, remove a list entry, or disconnect Battle.net for a friends-only party. Verify restoration to the captured method while still leader. Missing Battle.net information must never activate FFA; a character-list match can qualify independently.
- [ ] **Manual control outdoors:** change loot manually after activation, then trigger unrelated quest/roster updates and change sound/window size. Outdoor FFA must stay paused, including after `/reload`. Check loot manually and toggle an Auto FFA option to resume. Start with manually selected FFA and verify the addon never claims it or restores it when trust changes outdoors. Dungeon Group Loot takes priority over that manual selection.
- [ ] **Recovery baselines:** separately begin with Group Loot, Round Robin, Need Before Greed and Master Loot if available. Disable both options after activation and verify actual restoration, including the original master person and unchanged quality threshold. If the master leaves or a restore is rejected, expect a persistent manual-review status even with both options off.
- [ ] **Restrictions and lifecycle outdoors:** verify solo, nonleader, raid and matchmade groups cause no activation. Test local/party combat, looting, and any exposed active restriction. Reload during/after an addon change, transfer leadership away and back, and leave/rejoin a party: no old restore instruction may run. Inspect loot manually whenever recovery is interrupted; FFA may remain set outdoors.

### Dungeon Group Loot — version 1.3, simulated only

- [ ] **Always-on priority:** with both Auto FFA options off, lead an ordinary 2-player home party into a dungeon with FFA selected. Verify Group Loot is requested, confirmed by the actual party setting, and shown in `/zkir`. Repeat with friends, listed characters, strangers and a disconnected member; trust must not select FFA or block Group Loot. Repeat in 3–5-player parties. No party announcements or threshold changes should occur.
- [ ] **Manual selection:** inside a dungeon, select FFA or another available method manually. Group Loot should return when safe. Repeat after an outdoor manual change paused FFA. Leaving the dungeon must preserve that pause; only a deliberate Auto FFA checkbox change or a known new party resumes outdoor FFA.
- [ ] **Safety waits:** while leading a dungeon party, test local combat, an open loot window and exposed game restrictions. The new Group Loot request must wait until those local restrictions clear. Another member's combat state alone must not impose the outdoor trust/combat check. Unavailable methods must be reported without false confirmation.
- [ ] **Location and authority:** test solo, nonleader, raid and instance-matchmade contexts: neither policy may change loot. Record the current leader client's `IsInInstance()` values for the dungeon (`true, "party"`) and outdoors (`false, "none"`). Move only a nonleader through the portal: policy must continue to follow the leader's location. If location data is unavailable or restricted, expect no new request, not a guessed policy. Do not mark unavailable test conditions passed.
- [ ] **In-flight transition:** enter a dungeon immediately after an outdoor FFA or restoration request. The issued request must settle or time out before Group Loot is requested. Confirm no conflicting simultaneous writes or repeated requests. Check the actual final method, not only a status message.
- [ ] **Leaving the dungeon:** first let outdoor FFA capture Round Robin or Master Loot, then enter a dungeon and confirm Group Loot. On leaving, the old baseline must not be restored. With enabled options and all members eligible, FFA should resume after its normal two-second check with Group Loot as the new baseline. Turn off both options to verify restoration now goes to Group Loot. Existing manual/interrupted pauses must instead keep outdoor FFA paused.
- [ ] **Reload and leader changes:** reload with FFA selected inside a dungeon, or promote another addon user while FFA is selected. The current leader should apply fresh Group Loot checks without reusing old FFA restoration ownership. The former leader must stop changing loot. Reload again after Group Loot is confirmed; no duplicate setter request should be needed.
- [ ] **Failure and retry:** where safely reproducible, reject or leave a Group Loot request unconfirmed. It should stop after one request and at most five seconds waiting, show manual-review guidance, and remain quiet through unrelated roster/quest updates. Toggle an Auto FFA checkbox or perform a genuine outdoor/dungeon or new-party transition to permit another attempt. If the condition cannot be reproduced in game, retain the simulated-only result.

- [ ] **Preferences:** change sound and solo warnings, then `/reload` and verify persistence. A new displayed attempt sounds once; repeated updates, reopening, preview and restored attempts stay silent. Test the actual client sound API and global sound settings. ## Party and failure checks

- [ ] Run 2-, 3-, 4-, and 5-player all-addon parties. Let a nonleader detect the event. All windows open, all members appear, one initial message comes from the actual leader, and one specific next-action message appears automatically with the UI ALL READY notice.
- [ ] Disable the addon on one member: Waiting becomes Unknown; the leader confirms only that missing information. Automatic evidence and leader confirmation remain visually distinct.
- [ ] Disable it on the leader: the alphabetically first responding full name sends the warning under its own name. Use the token-bound PARTY command to confirm the leader/other nonresponders; test Ready and Not ready, stale token rejection, and `/p ZKIR status`.
- [ ] Try confirming a disconnected or automatically blocked member; it must fail. A responding client whose facts stop arriving must not be manually bypassed.
- [ ] Change an unrelated quest: manual confirmations remain. Change relevant quest facts, disconnect/reconnect, join/leave, or promote a new leader: old confirmations disappear and only the current leader has controls.
- [ ] Open the same interaction simultaneously. Repeat opening it, close/reopen the window, reload the leader, reload other clients, and reload everyone. Check announcement counts and stale approval rejection.
- [ ] Start a legitimate new attempt with `/zkir retry`; every old confirmation/token becomes invalid. Confirm NPC state separately: this command cannot reset the encounter.
- [ ] Restrict/unregister messaging or interrupt connectivity. Expect suspended/Unknown readiness without Lua errors, retries flooding chat, or a false proceed notice. Restore communication, coordinate a new attempt, and retry. Document silent initial partitions as a delivery limitation.
- [ ] Run solo: the pre-action warning appears, no PARTY traffic occurs, and normal game controls remain usable.

For every actual acceptance, record invitation received, accepted, quest present in log, and eventual credit as separate observations. A green row is not evidence that any of those later events happened.
