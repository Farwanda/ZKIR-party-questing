# Coordination and delivery boundaries

The pure state machine is in `Core.lua`; `Facts.lua` evaluates only action-relevant snapshots. `WoW.lua` owns events, interaction context and guarded communication; `API.lua` shares safe reads with the independent Auto FFA module. `Rules.lua` is the entire runtime catalogue, and `Messages.lua` formats its factual text for the UI and chat. `UI.lua` uses one renderer for real warnings and an isolated preview. `Widgets.lua` shares small UI constructors with `Settings.lua`, which owns preferences and their defaults. Rendering is coalesced across nested events; unchanged text and hidden settings are not repeatedly rewritten. Protocol and loot timers still run normally.

Settings and preview do not create events, publish facts, send messages, confirm readiness, or replace the real engine. Suppressing solo presentation does not suspend the protocol when joining a party. Solo attempts do not consume PARTY announcement slots, so a subsequently formed group can receive its initial warning **only while the action is still pending**. Observed actions cancel pending announcements; accepting, turning in or choosing dialogue solo cannot queue a warning for a later group. `/zkir` always opens settings; `/zkir show` explicitly reopens a real warning. Sound is guarded and deduplicated across repeated updates and concurrent detections; preview, manual reopening, and restored attempts are silent. The Loaded indicator confirms addon code is running, not message delivery or live server behavior.

Packets use the versioned `ZKIRPQ1` prefix, only PARTY, at most 255 bytes, and roster-resolved full player identities. No incoming text is executed. Unknown versions, outsiders, ambiguous short names, malformed event envelopes, old attempts, retired boots, and older fact sequence numbers are ignored. Party addon messages are cooperation between peers, not an authenticated security boundary against a deliberately malicious party addon.

An event is a rule, observable NPC instance (or explicit unknown context), unique attempt key, and parent attempt. Concurrent detections of the same event converge deterministically. Announcements already recorded for a concurrent alias carry into the chosen key. Retry is explicit and rate limited to once per five seconds. Quest acceptance/turn-in and observed gossip selections retire the preparation. Both `SelectOption` and native `SelectOptionByIndex` are observed without replacing game controls. Captured gossip context allows the immediate post-hook to work after native cleanup clears the NPC, with a one-second bound after closure. The observer conservatively retires preparation on any selection at that NPC; it cannot prove that the consequential option was chosen. Repeated action observations are idempotent.

The panel docks only when the captured quest/offer and exact NPC/object GUID match the active event and the native frame is visible. Late frame creation and show/hide transitions are observed. Its lifetime is independent of the dialogue: remote recipients and closed or unrelated dialogues use the same compact floating fallback. A collapsed action notice does not assert that every participant accepted a quest or received credit. A shared-quest invitation remains a prompt to act, not proof of local acceptance. Presentation changes do not create attempts or clear announcement history.

Quest-based events preserve an observed GameObject GUID as context too, so distinct Broken Traps cannot reuse an attempt. Opening the same retired NPC does not automatically discover a new stage: Pusillin's later stops and a changed Rocknot hand-in plan need `/zkir retry`. Nagmara's repeat-route history is part of relevant evidence, but helpers are not required to have that actor-only unlock.

Automatic readiness follows the action. An acceptance checks access before the first player takes the quest. Mason's collective hand-in instead checks current quest holders' objective completion; an incomplete holder is blocked, while an absent quest leaves the participant's role Unknown. Conflicting sourced minimum levels leave the disputed interval Unknown rather than certifying eligibility or inventing a blocker.

Every three seconds, clients preparing an action repeat the session, boot identity, and their latest fact revision. Facts expire after twelve seconds. A discovered peer that stops heartbeating suspends synchronization. Send failure latches suspension until a new attempt, so a restricted API cannot create an automatic retry storm. Ordinary quest updates with identical relevant facts do not change the revision. Relevant changes and roster/leadership transitions advance evidence versions even if the values later return to their previous state.

After an observed action, clients stop evaluating/publishing facts, accepting confirmations, proposing announcements and checking peer expiry for that attempt. They repeat exact-key retirement (`X`) so existing peers can recover a missed action without opening a warning on a new client. Retired event envelopes (`E`) are repeated only within the original party roster to reconcile simultaneous detections; a roster change permanently clears that scope. Incoming retired envelopes can end the same or a concurrent active attempt, but cannot open an idle client's window or replace an unrelated interaction. Retirement survives concurrent alias selection and reload; only an explicit fresh attempt resets it.

Manual decisions bind to the attempt, full roster/connectivity/leader, responding client boots, and relevant fact revisions. They are never saved. Repeated packets cannot reverse a newer manual decision. A previous verified blocker is retained when its replacement is merely missing evidence; new positive automatic evidence or a deliberately new attempt is required. Disconnection always overrides manual decisions. Missing facts from a previously responding addon cannot be replaced by manual Ready. A leader without the addon can confirm via authentic PARTY messages containing the current fingerprint token; fallback clients acquire no leader authority.

The actual leader is preferred when responding. Otherwise, responding names sort deterministically. After discovery and stable evidence, the sender proposes each announcement. Every discovered peer must acknowledge the same evidence fingerprint; next-action proposals additionally require that peer's all-ready state. Peers reserve the announcement in per-character SavedVariables **before** acknowledgement, and the sender records it before attempting chat. Receipts are repeated. Initial and next-action messages each have one slot per attempt, surviving normal reloads and leadership changes. They are not resent merely because readiness toggles. A new attempt has new slots.

This favors avoiding duplicates over retrying uncertain chat. If the sender crashes or the chat API refuses the call after reservation, the message may be omitted. The UI retains the warning. WoW chat provides no delivery acknowledgement, and SavedVariables are flushed by the game on logout/reload, not synchronously to disk. A hard crash can lose the latest saved state.

**No timeout can prove that a silent leader lacks the addon.** Fallback assumes responding clients can discover each other over PARTY during the settling window. Previously undiscovered partitions can each elect a sender; unconditional exactly-once delivery is impossible without a server authority or delivery acknowledgements. Normal delayed discovery, duplicate/reordered packets, lost acknowledgements, reloads, and detected communication failures are simulated. An arbitrary initial partition, server rejection after apparent success, and client crashes remain delivery limitations, not guarantees hidden by the UI.

Readiness is a fresh preparation snapshot, with normal communication latency. It cannot prevent another player acting, prove shared layer/range, repair a script, or guarantee credit. Unsupported or secret APIs produce missing evidence. Raids and battleground/instance-channel coordination are outside this 2–5-player PARTY scope.
